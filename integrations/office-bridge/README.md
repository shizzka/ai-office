# AI Office ↔ DCM / job-hunter

Офис: <http://192.168.21.166:3000/office/stream>.
Доска задач (только чтение, без пароля из LAN): <http://192.168.21.166:3000/office/board>.
Управление (с входом): <http://192.168.21.166:3000/office/admin>.
WebSocket: `ws://192.168.21.166:3101/mcws`.

`bridge.py` — наблюдатель на Python 3, только stdlib. Каждые 18 секунд читает
`/proc`, метаданные/последние записи Claude transcripts, `tmux list-panes`,
логи DCM/JH и историю Git DCM. Скрипты проектов не запускаются; SSH-соединения
не создаются; tmux не изменяется. Записи выполняются только в SQLite офиса; для источников используются
только операции чтения. В юните включён `NoNewPrivileges=yes`.

## Команда и источник активности

| Агент | Источник |
|---|---|
| 🏗️ Ярик | `claude`, проект из последних записей transcript (включая cwd `/home/q`), запись моложе 120 с |
| 💻 Лёха | живой `codex exec`, `gpt-6.1-sol` |
| 🔍 Ася | `gpt-6-astra`, CRITIC* / ACC* |
| 📐 Иваныч | `gpt-6-astra`, TABLES* / NORM* |
| 🎨 Тая | `gpt-6.1-terra`, VISUAL* |
| 🧪 Саня | MISSION* / TESTER*, известный процесс JH-тестера либо его локальный лог моложе 120 с |
| ⚙️ Мотя | `dcm-qa/worker-run.sh`, команда из argv, шаг из локального stdout-лога |
| 🛡️ whoami | `sec-watch/nightly.sh` / `weekly.sh`; в idle дата последнего `runs/*/report.md` |
| 📟 Люда | Claude в `jh-ops`, свежесть transcript; сессия без свежей записи — idle |

Проект определяется по `-C` / `--cd`, задание — по файловому `/proc/PID/fd/0`
(любое имя), иначе по `-o` / `--output-last-message`. Pipe stdin не читается.
Node-обёртка и нативный Codex учитываются один раз.
`-C /home/q/ai-office` и `--add-dir /home/q/work/office-bridge` обозначают
служебную работу: агент работает с подписью «Офис: <задание>», карточки DCM/JH
не создаются. Для офиса и JH модель определяет исполнителя независимо от имени
файла: sol → Лёха, astra → Ася, terra → Тая; без явной модели — Лёха.

Описания DCM берутся из `dcm-qa/fixes/board-titles.json` по коду этапа, затем
из строки `# Задание …:` в `<этап>-task.md`, затем сохраняется прежний текст.
Файлы перечитываются каждый цикл (18 с), в том числе при замене через rename.
На доске описание показано одной строкой, полное доступно при наведении;
технический статус хранится отдельно в `tasks.status_detail` и показан мельче.
`F0: регрессия перепроверена — ЗЕЛЁНАЯ (…)` сбрасывает предупреждение и urgent;
последующая красная регрессия снова поднимет предупреждение.

JH не требует pipeline.log или соглашений об именах заданий. Запущенные
`codex exec -C /home/q/work/job-hunter*` (включая worktrees) создают карточку
из первого Markdown-заголовка stdin-файла и следующей содержательной строки.
Без доступного stdin заголовком служит имя `-o`. Пока процесс жив — «в работе»;
после выхода — «готово», если отчёт `-o` существует и последний лог не содержит
ошибку, иначе ⚠. Последняя запись EXIT имеет приоритет над более ранними
ошибками; ошибка после EXIT=0 снова считается неуспехом. Читается последний
файловый stdout/stderr, до 16 KiB. Если файлового лога нет, проверяется наличие
отчёта. Завершение — наблюдаемый результат, не независимая QA-приёмка.
Реестр запусков `office_bridge_state['jh:jobs']` сохраняет источники и результат;
boot ID, PID и время рождения процесса предотвращают дубли после рестарта
моста и отличают повторный запуск с тем же PID. Завершённый результат фиксируется,
чтобы повторное использование файла лога не меняло историю старой задачи.
Мост должен хотя бы один раз увидеть живой процесс; короткие задания между
опросами без журнала восстановить невозможно. Необязательный
`job-hunter/pipeline.log` поддерживает произвольные этапы `старт X` /
`конец X: EXIT=…`, имеет отдельный курсор событий и не добавляет этапы DCM.

Для Claude читается хвост JSONL (до 64 KiB) своей сессии из `~/.claude/projects/`.
Последнее упоминание `work/dcm*`, `dcm-qa`, `dcm-local` или `job-hunter` в сообщениях
определяет проект; cwd используется как запасной источник. Последний assistant-блок
`thinking` даёт статус «думает», иначе свежая сессия — «работает».
`--resume` / `--session-id` позволяют найти transcript в исходном каталоге при смене cwd.
При нескольких Claude с одинаковым cwd без ID используется самый свежий transcript
этого каталога; чужие сессии из других каталогов не подмешиваются.

Доска опрашивает GET `/api/tasks`, `/api/projects`, `/api/agents`, `/api/activity/feed`
раз в 10 с. Анонимное чтение этих API доступно по private IP/localhost согласно
политике Host в middleware. Любые методы записи API требуют действительный JWT
(Bearer или cookie); единственное исключение — POST входа `/api/auth/login`.
LAN больше не выдаёт автоматические права администратора. `/office/admin` требует
входа и в LAN. Проверки доступа: `cd /home/q/ai-office && npm test`.

## Архив и восстановление одной командой

Восстановить прежнюю видимость старой команды, задач, проектов и событий:

```bash
python3 /home/q/work/office-bridge/bridge.py --restore-legacy
```

Снова скрыть старую команду и прежний контент:

```bash
python3 /home/q/work/office-bridge/bridge.py --archive-legacy
```

Перезапуск моста не отменяет восстановление. Новая команда остаётся видимой.
Сохраняются первоначальные флаги: то, что было архивировано до установки, при
восстановлении остаётся архивным. Данные, комментарии, история и прямые ссылки
на детали не удаляются. Состав старой команды фиксируется один раз при установке.

## Запуск и обслуживание

Установленные user units (исходники в `systemd/`):

```bash
systemctl --user status ai-office.service ai-office-ws.service office-bridge.service
journalctl --user -u office-bridge.service -n 30 --no-pager
systemctl --user restart office-bridge.service
```

Офис запускается командой `npm run start -- --hostname 0.0.0.0`, WS —
`node worker/ws-server.js`. Все три юнита включены в `default.target`, имеют
`Restart=always`. Перезапуск `ai-office.service` перезапускает и его WS-сервис.
Работа после выхода из пользовательской сессии зависит от системной настройки
linger; мост её не меняет.

Разовый сбор:

```bash
python3 /home/q/work/office-bridge/bridge.py --once
```

Параметры: `--db`, `--work-root`, `--interval` (18 с по умолчанию), `--ws-url`.
`--work-root` задаёт расположение логов; правила идентификации процессов привязаны
к текущему `$HOME/work`.

После изменения исходников офиса:

```bash
cd /home/q/ai-office
npm run db:migrate
npm run build
systemctl --user restart ai-office.service
```

Установка на этой машине заново (после сборки и миграции):

```bash
install -m 0644 /home/q/work/office-bridge/systemd/*.service /home/q/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now ai-office.service ai-office-ws.service office-bridge.service
```

## Данные и конвейер

API не покрывает атомарную синхронизацию и архивирование, поэтому мост пишет
напрямую в `data/database.sqlite`: `foreign_keys=ON`, busy timeout 10 с,
одна транзакция на цикл. Миграция добавляет только `archived` в `agents`,
`tasks`, `projects`, `activity_logs`; служебные таблицы `office_bridge_state`,
`office_bridge_legacy`, `office_bridge_legacy_tasks`, `office_bridge_legacy_projects`,
`office_bridge_legacy_activity`
хранят курсор событий и снимок прежней видимости. Идентификаторы новых строк
имеют префикс `bridge-`.

Задачи: FIX-4, F1A, F1B, F1C, F2, F3, ACC и этапы, обнаруженные в `pipeline.log`.
`chain.sh` только читается. Старт → в работе; EXIT=0 / ветка feat/* → ревью;
коммит в истории dev → готово. Для приёмки проверяется вхождение хеша из строки
`приёмка влита …` в историю dev, даже если сообщение коммита не содержит `ACC`.
Готовый непустой `*-out.md` при ротации лога даёт ревью (без утверждения, что QA
пройден). Отсутствие новой записи не возвращает уже наблюдавшийся этап в очередь.
Живой Codex имеет приоритет над старой записью о завершении. СТОП / КРАСНАЯ /
RESULT False / ненулевой EXIT → urgent с `⚠` в заголовке и исходной строкой
ошибки в описании. Ошибку снимает новый старт или явная запись о слиянии.

Каждая законченная строка `pipeline.log` попадает в activity с именем агента.
Первый запуск импортирует прежние строки. Курсор и события коммитятся вместе:
повторный запуск не дублирует ленту. Учитываются ротация и усечение, незавершённая
последняя строка ждёт перевода строки. WS `/emit` уведомляется после коммита;
недоступность WS не откатывает данные, клиент также получает обновления опросом.

## Ограничения

- Наблюдение локальное: нет SSH-запросов на воркер или LLM-ноут. Для удалённого
  JH-тестера локальный свежий лог — косвенный сигнал; это подписано в статусе.
- Для Claude без явного `--resume` берётся самый свежий transcript каталога cwd;
  несколько сессий с одинаковым cwd могут разделять сигнал активности.
- Открытая, но молчащая сессия показывает idle. Входной pipe Codex не читается,
  чтобы не отнять stdin у работающего агента; тогда используется имя `-o`.
- Расходы Codex/Claude этим мостом не измеряются. Исторические расходы скрытых
  OpenClaw-агентов не выдаются за расходы новой команды.
- Состояния из лога и Git отражают наблюдаемые этапы, а не результат независимой
  приёмки продукта. Историческая красная регрессия сохраняется как urgent.
- Существующие пользовательские маршруты ручного запуска/отправки задач в AI
  Office не переподключены к DCM/JH. Мост показывает состояние и сам задач не запускает.

Файловые mount namespace ограничения systemd (`ProtectHome`/`ProtectSystem`)
на этой машине мешают чтению `/proc/PID/cwd` и stdin чужих процессов того же
пользователя, поэтому не включены. Тестовый read-only probe подтвердил причину;
`NoNewPrivileges` чтению не мешает. DCM/JH наблюдаются исключительно через
читающие операции в коде моста.

## Шарик: плановые прогоны job-hunter (OFFICE-5)

`jh_observer.py` читает только `~/.job-hunter/profiles/*/scheduled-search.log`,
профильную/общую `analytics_events.jsonl`, `/proc` и метаданные замков
`/tmp/jh-search-*.lock`. Замки не открываются и не захватываются. Поиск,
боты, cron и watchdog не запускаются и не меняются.

Шарик (`bridge-sharik`, место 855×500 рядом с Людой) показывает `working`
только при живом `run.sh --profile … search` / нативном CLI или занятом
процессом замке. Оставшийся `start` сам по себе не означает работу.
Живой `bot-daemon` отмечается отдельно как чат; он не делает поиск активным.
Между прогонами — `idle`, последний start/end/rc и общее указание утро/вечер;
при ненулевом rc — ⚠. Карточки задач для этой рутины не создаются.

В БД попадают только фиксированный текст, числа и время: `qa` → «основной»,
`client_*` → «клиент 1/2…» (сортировка каталогов), `qa-dev`/`marina-dev` → «dev».
Неизвестные профили скрываются. Сырые строки расписания, payload аналитики,
имена каталогов и внутренние идентификаторы аккаунтов/прогонов не сохраняются.
Файл конкретного профиля определяет профиль независимо от `profile_id` внутри
события; общий файл используется только при явном совпадении `profile_id`.

Счётчики связываются с единственным `search_started` рядом со стартом расписания:
`search_finished.found`, `.applied`, `.funnel.evaluated`. Пока итогов нет,
подтверждённые оценки — уникальные `decision` с `evaluation_present=true`,
отклики — уникальные `application_result.outcome=sent`. «Ошибок этапов» —
число уникальных записанных `stage_failed`; ошибки LLM/попытки/неопределённые
результаты не складываются с ними. При отсутствии связи счётчики скрываются.
Читается хвост до 32 MiB аналитики; без полного начала прогона производные
нули не выводятся. Между изменениями файлов используются числовые проекции
в памяти. Конец, записанный раньше аналитики, дополняется без дубля события.

Проверки: `python3 -m pytest -q tests`. Все фикстуры синтетические;
общие тесты `tick` изолированы от настоящего `~/.job-hunter`.
Лист героев: `output/heroes-sheet.png`, источник — `ai-office/tests/preview-heroes.mjs`.
